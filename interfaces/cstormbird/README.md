# A C-interface for the Stormbird library

This crate implements a C-interface to the main structures and methods in the Stormbird library, so that the library can be used from other languages without a dedicated Stormbird interface. As most languages understand the C-ABI, a general C interface might be useful.

The functionality follows the [pystormbird](../pystormbird/) package closely. The same structures are available, with the same methods, and the C functions are named after the structure and the method in pystormbird, e.g., `complete_sail_model_simulate_steady_state_condition` for `CompleteSailModel.simulate_steady_state_condition`. See the [Stormbird book](https://jarlekramer.github.io/stormbird_book_pages/) for a description of the models.

The header file, `include/cstormbird.h`, is generated by `cbindgen` when the crate is built.

## Conventions

Rust structures that cannot be represented directly over a C-ABI, because they contain enums with data or variable sized data, are handled as *opaque handles*. These are `CompleteSailModel`, `LiftingLineSimulation`, `WindCondition` and `SimulationResult`. A handle is created by one of the `*_new_*` functions, which return `NULL` on failure, and must be released with the matching `*_drop` function. Functions that run a simulation return a new `SimulationResult` handle, which must also be released.

Functions that return a single value use the natural type, and return `NaN`, or `-1` for counts and integers, for a null pointer input. The remaining functions return an `int32_t`, which is either the number of elements written to an output array, or one of the following:

| Code | Meaning                                                                          |
|------|----------------------------------------------------------------------------------|
| `0`  | Success, for functions that do not return a count                                |
| `-1` | One of the input pointers is null                                                |
| `-2` | An array length is zero, or does not match what the model expects                |
| `-3` | A string is not valid UTF-8, or not valid JSON for the given structure           |
| `-4` | The wind condition does not use the velocity variation that is needed            |
| `-6` | An input value is not valid, e.g., a wing index that is out of range, or span locations that are not increasing |

The code `-5` was used by an earlier version, and is not used anymore.

Arrays are always owned by the caller. Functions that write to an array take the length of the array as input, and write at most that many elements. Vectors are passed as 3 doubles per point.

## Error messages

The error codes say *that* something went wrong, and `stormbird_last_error_message` says *what*. It returns a description of the most recent failed call on the calling thread, or `NULL` if nothing has failed yet, and should only be read after a function has reported a failure. Successful calls leave it untouched. The string is owned by the library and is only valid until the next failing call on the same thread, so copy it if it is needed after that. `stormbird_clear_last_error` resets it.

Invalid settings in a setup string, e.g., a wing with fewer than two section points or an invalid controller, are reported when the model is created:

```c
CompleteSailModel *model = complete_sail_model_new(setup_json_string);

if (model == NULL) {
    fprintf(stderr, "Could not build the sail model: %s\n", stormbird_last_error_message());
    return 1;
}
```

## The two entry points

`CompleteSailModel` combines a lifting line simulation with a wind environment and an optional controller, and is the interface to use when the sails should be simulated as a complete system, either in steady state conditions or in the time domain. `LiftingLineSimulation` is the lifting line simulation on its own, for the cases where the freestream velocity is computed elsewhere, such as by a CFD solver.

### Complete sail model

The model is created from the JSON representation of a `CompleteSailModelBuilder`, e.g., generated with [stormbird_setup](../stormbird_setup/). The controller is optional, which `complete_sail_model_has_controller` reports. Without a controller, the sails are operated with the local wing angles and internal states that are set directly on the model, and the `complete_sail_model_apply_controller_*` functions do nothing.

The main functions are:

- `complete_sail_model_simulate_steady_state_condition` and `complete_sail_model_simulate_optimal_steady_state_condition`: steady state simulations, where the controller, if any, is iterated until it converges. The `_simple_output` versions write the total force, moment and input power of each sail to an array of `SingleSailResult`.
- `complete_sail_model_do_step` and `complete_sail_model_do_multiple_steps`: time-domain simulations with the current sail settings.
- `complete_sail_model_freestream_velocity`: the apparent wind at all the points where the simulation needs it.
- `complete_sail_model_apply_controller_based_on_wind_condition`, `_based_on_freestream` and `_based_on_simulation_result`: updates of the sail settings with the controller.
- `complete_sail_model_set_local_wing_angles`, `complete_sail_model_set_internal_state`, and the getters `complete_sail_model_local_wing_angles` and `complete_sail_model_internal_state`.
- `complete_sail_model_set_internal_state_linear` and `complete_sail_model_set_internal_state_piecewise_constant`: internal states that vary along the span of a single sail.

By default, the ship velocity is a scalar, and the ship is assumed to move in the opposite direction of the `zero_direction_vector` in the wind environment. The versions of the functions that end with `_with_ship_velocity_vector` take the velocity of the ship as a vector of 3 doubles instead, e.g., when it comes from an external motion simulation: `complete_sail_model_simulate_steady_state_condition_with_ship_velocity_vector`, `complete_sail_model_simulate_optimal_steady_state_condition_with_ship_velocity_vector`, `complete_sail_model_do_step_with_ship_velocity_vector` and `complete_sail_model_freestream_velocity_with_ship_velocity_vector`. `complete_sail_model_ship_velocity_vector` returns the vector that corresponds to a scalar ship velocity.

```c
#include "cstormbird.h"

CompleteSailModel *model = complete_sail_model_new(setup_json_string);
WindCondition *wind = wind_condition_new_power_model_with_default_shape(1.57, 10.0);

int nr_sails = complete_sail_model_get_number_of_sails(model);
SingleSailResult *results = malloc(nr_sails * sizeof(SingleSailResult));

complete_sail_model_simulate_steady_state_condition_simple_output(
    model, wind, 5.0, 1.0, results, nr_sails
);

/* The same condition, with the ship velocity given as a vector */
double ship_velocity_vector[3] = {-5.0, 0.0, 0.0};

SimulationResult *result = complete_sail_model_simulate_steady_state_condition_with_ship_velocity_vector(
    model, wind, ship_velocity_vector, 1.0
);

simulation_result_drop(result);
free(results);
wind_condition_drop(wind);
complete_sail_model_drop(model);
```

### Lifting line simulation

The simulation is stepped forward in time with `lifting_line_simulation_do_step`, which needs the freestream velocity at the points given by `lifting_line_simulation_get_freestream_velocity_points`. With a dynamic wake that set of points grows as the wake develops, so it must be queried before each time step. The motion of the sails is set with the `lifting_line_simulation_set_translation_*`, `_set_rotation_*` and `_set_velocity_*` functions, and the sail settings with the same functions as for the complete sail model.

```c
LiftingLineSimulation *simulation = lifting_line_simulation_new(setup_json_string);

double angles[1] = {0.17};
lifting_line_simulation_set_local_wing_angles(simulation, angles, 1);

int nr_points = lifting_line_simulation_get_number_of_freestream_velocity_points(simulation);
double *freestream = malloc(3 * nr_points * sizeof(double));
/* fill in the freestream velocity at each point, 3 doubles per point */

SimulationResult *result = lifting_line_simulation_do_step(
    simulation, time, time_step, freestream, nr_points
);

double force[3];
simulation_result_integrated_forces_sum(result, force);

simulation_result_drop(result);
free(freestream);
lifting_line_simulation_drop(simulation);
```

## Wind conditions

A `WindCondition` is created with one of `wind_condition_new_constant`, `wind_condition_new_power_model`, `wind_condition_new_power_model_with_default_shape`, `wind_condition_new_logarithmic_model` or `wind_condition_new_from_json_string`. Gusts can be added with the `wind_condition_set_*_gust` functions, and the velocity at a given height and time can be queried with the `wind_condition_*_velocity_*` functions.

## Simulation results

A `SimulationResult` is returned by the simulation functions, and can also be read from a JSON file with `simulation_result_new_from_json_file`, e.g., a result written by the actuator line model. The data follows the `SimulationResult` class in pystormbird:

- `simulation_result_time`, `simulation_result_iterations`, `simulation_result_residual`, `simulation_result_nr_of_wings` and `simulation_result_nr_of_span_lines`.
- `simulation_result_wing_indices`: the first and one past the last line element of each sail.
- `simulation_result_integrated_forces_sum`, `simulation_result_integrated_moments_sum` and `simulation_result_input_power_sum`: totals for all the sails.
- `simulation_result_integrated_forces`, `simulation_result_integrated_moments` and `simulation_result_input_power`: values for each sail. The forces and moments are written as an `IntegratedValues` struct for each sail, with the circulatory, sectional drag, added mass, gyroscopic and total contributions.
- `simulation_result_as_simplified`: the total force, moment and input power of each sail, as an array of `SingleSailResult`.
- `simulation_result_ctrl_points` and `simulation_result_sectional_forces`: the control points and the forces on each line element. The forces are written as a `SectionalForces` struct for each line element, with the same contributions as above.
- `simulation_result_force_input_*`: the input used to compute the forces on each line element, i.e., the circulation strength, the velocity, the angle of attack, the internal state of the section models, the amount of stall and the acceleration, as well as the angular velocity of the sails.

## Not available in the C interface

Some parts of pystormbird are not available in the C interface, as they are mainly useful for analysis and setup in Python: the section models, the line force model on its own, the wind environment, the smoothing functions, the export of the wake as VTK data, and the reading of a history of simulation results from a file.
