# Change log Stormbird

This file contains an overview of the changes made to the Stormbird Rust library. The other crates and packages in the repository have their own change logs.

## 0.14.0 - Unreleased
### Breaking changes
- The lift-induced velocities at the control points are now always computed in two parts: the velocities induced by the wake of the same wing (self-induced) and by the wakes of the other wings (other-induced). The `FrozenWake` stores both parts in the new `InducedVelocities` struct, for the `fixed_velocities` and the `induced_velocities_at_control_points`, and `FrozenWake::initialize` takes the `wing_indices` of the line force model instead of the number of line elements. The total is given by `InducedVelocities::total`.
- The `velocity_corrections` field in the `Iterative`, `QuasiSteadyIterativeBuilder` and `Linearized` solvers is replaced by `induced_velocities`, with the new `InducedVelocitySettings` struct. It has three fields:
  - `neglect_self_induced_velocities`, moved from the `DynamicWakeBuilder`.
  - `self_induced_correction`, a new `SelfInducedVelocityCorrection`, applied to the self-induced velocities only.
  - `total_correction`, a `TotalVelocityCorrection` with the same options as the old `VelocityCorrections` enum, applied to the sum of the self-induced and the other-induced velocities.

  In JSON input, `"velocity_corrections": X` becomes `"induced_velocities": {"total_correction": X}`, which gives the same results as before.
- `neglect_self_induced_velocities` is removed from the `DynamicWakeBuilder` and the `WakeSettings` of the dynamic wake. Set it in the `induced_velocities` of the solver instead.
- The settings of the lifting line correction in actuator line simulations are split into settings that are common to all wake models, which stay in the `LiftingLineCorrectionBuilder`, and a new `wake` field with the `CorrectionWakeBuilder` enum, for the settings that are specific to each wake model. `wake_length_factor` and `virtual_extension_factors` are moved into the default `Straight` variant, so `"wake_length_factor": 100.0` in JSON input becomes `"wake": {"Straight": {"wake_length_factor": 100.0}}`. Input files that only use the common settings (`symmetry_condition`, `initialization_time`, `reference_core_length_factor`, `include_wing_interactions` and `max_correction_ratio`) are unchanged, and give the same results as before.
- `LiftingLineCorrectionBuilder::build` returns a `Result`, and checks the settings with the new `LiftingLineCorrectionBuilder::check_settings`, which is also called from `ActuatorLineBuilder::check_settings`.
- The lifting line correction is split into `LiftingLineCorrection::update`, which updates the wake model from the sampled velocity, and `LiftingLineCorrection::velocity_correction`, which computes the correction. `ActuatorLine::solve` calls the new `ActuatorLine::update_lifting_line_correction` before the corrected velocity is computed. The shared settings are in the new `CorrectionSettings` struct, and `velocity_correction_isolated_wings` and `velocity_correction_all_wings` are replaced by one implementation for each wake model, where isolated wings only include the wakes of the same wing.
- `LiftingLineCorrection::update` takes the circulation from the previous time step (reference and projected), the time and the time step, which are used by the new dynamic wake. `ActuatorLine::update_lifting_line_correction` takes the time and the time step, and passes the circulation from the last simulation result.
- `WakeSettings::end_index_induced_velocities_on_wake` in the dynamic wake is replaced by `points_with_induced_velocities`, a range of point indices, given by the new function `points_with_induced_velocities` in `dynamic_wake::settings`. See the bug fixes.
- `DynamicWake::induced_velocities_from_free_wake` is replaced by `DynamicWake::induced_velocities_from_free_wake_per_line_element`, which returns the velocities from the panels shed from each line element separately, so that the `FrozenWake` can split them into self-induced and other-induced velocities. The unused `DynamicWake::induced_velocities_from_first_panels` is removed.
- `remove_span_velocity` in the `SamplingSettings` of the actuator line is true by default, see the bug fix for the angle of attack below. Set it to false to keep the sampled velocity along the span, which then only affects the size of the forces and the direction of the drag, as the angle of attack no longer depends on it.
- The unused `LineForceModel::lift_from_coefficients` is removed.

### Features
- The self-induced velocities can be neglected in quasi-steady simulations as well, not only in dynamic simulations.
- New `StraightPanels` wake model for the lifting line correction in actuator line simulations. The wake is straight, as the default `Straight` wake, but split into panels in the streamwise direction, with the new `StraightPanelWakeBuilder` settings: `wake_length_factor`, `nr_panels_per_line_element`, `first_panel_relative_length`, `reference_core_evolution_length_factor` and `far_field_ratio`. The panels get gradually longer downstream. With the `reference_core_evolution_length_factor`, the core length of the reference model grows from the small reference value to the viscous core length of the projection width over the given distance along the wake, relative to the average chord length, following a quarter sine period. The two wake models are then equal downstream, so that the tip vortices of an upstream wing do not give large, singular, corrections at a downstream wing when the wing interactions are included. The panels use the same `DynamicWake` structure as the dynamic wake in the lifting line simulations. Virtual extensions are only available for the `Straight` wake for now.
- New `Dynamic` wake model for the lifting line correction in actuator line simulations, with the new `DynamicCorrectionWakeBuilder` settings: `nr_panels_per_line_element`, `first_panel_relative_length`, `last_panel_relative_length`, `shape_damping_factor`, `reference_core_evolution_length_factor` and `far_field_ratio`. The wake is a free wake, where the first free row of points follows the sampled velocity at the control points, and the other points move with the velocity sampled from the CFD flow field at the wake points, with no induced velocities from the wakes themselves. A new row of panels is shed in each time step, with the circulation from the previous time step, and the wake is only updated in the first call with a new time, so that outer iterations do not move it. The CFD solver sets the velocity at the wake points with the new `ActuatorLine` functions `wake_points_to_sample`, `nr_wake_points_to_sample`, `set_wake_point_velocity_at_index` and `set_wake_points_velocity`. Values that are not finite are ignored. The velocity at the wake points is sampled in Stormflow and in the OpenFOAM interface.
- The wake of the lifting line correction can be exported as a legacy VTK file, with `ActuatorLine::correction_wake_as_vtk` and `ActuatorLine::write_correction_wake_to_vtk_file`, for the `StraightPanels` and `Dynamic` wakes. The file has the geometry of the panels, the strength and the core length of each panel in both wake models, and, for the dynamic wake, the sampled velocity at the points. `polygons_as_vtk` takes vector data for the points, which is empty for the existing exports of the lifting line wakes.
- New `LineForceModel::average_chord_length`.
- New `ViscousCoreLengthEvolution::sin_increase_factor`, with the blending factor of the `SinIncrease` evolution of the viscous core length, which is also used for the growth of the reference core length in the lifting line correction. `DynamicWake::panel_point_indices` is now public.
- New `self_induced_correction` in the `InducedVelocitySettings`, so that the magnitude of the self-induced velocities can be limited with `MaxInducedVelocityMagnitudeRatio`, without limiting the velocities induced by other wings. It can be combined with the `total_correction`.

### Bug fixes
- The dynamic wake computed induced velocities at the wake points that `ratio_of_wake_affected_by_induced_velocities` should exclude. With the default ratio of 0.0, the induced velocities were still computed at the first row of points (the span points on the wings), in every time step. The result was only used with the `ActualVelocity` direction of the first wake points, where it was also inconsistent: the first row behind the wings did not get induced velocities, and the last point of the affected rows was always left out. The induced velocities are now only computed at the points where they are used. The ratio gives the fraction of the rows that are moved with the stored velocity (all rows except the first and the last two), and with `ActualVelocity` the wings and the first free row always get induced velocities. Effects:
  - A full time step of a dynamic simulation with the default settings is about twice as fast (22 ms to 12 ms in the `induced_velocity_benchmark`). The results are unchanged with `Freestream` or `Chord` and a ratio of 0.0 or 1.0.
  - With `ActualVelocity`, the direction of the first wake panels now includes the induced velocities at both ends of the panel. In a test with a rectangular wing, the forces changed by up to 2e-4 relative to the previous version with a ratio of 0.0.
  - With ratios between 0.0 and 1.0, the last affected row is now complete, which changed the forces by up to 2e-5 relative in the same test.

- The far field model of the vortex panels, a point doublet without a viscous core, was used inside the viscous core when the panels were small compared to the core length, since the far field distance was only relative to the size of the panel. The far field distance is now `far_field_ratio` times the side length of the panel or the viscous core length, whichever is larger. The error was largest in the `Dynamic` wake of the lifting line correction, where one row of panels is shed per CFD time step, so that the panels are much shorter than the viscous core of the projection width. There, the mean correction along the span of a rotor-like wing was about 25 % too large, while the ends were almost unaffected. With the fix, the `Dynamic` wake is within 1 % of the `Straight` wake for a straight wake. The cost of the correction increased by about 4 %. In the dynamic lifting line simulations in the rotor sail example, with a viscous core that grows to 1.5 diameters, only the case where the wake of one rotor hits the other changed, by 1.7 % in drag.

- The direction of the viscous lift force (the post-stall lift, when `include_viscous_lift_in_the_circulation` is false, which is the default) was computed from the span lines in the body fixed coordinate system also when the output was in the global coordinate system (the default), while the velocity was global. The force direction was therefore wrong when the rigid body rotation changed the direction of the span lines, e.g., roll or pitch of a ship with vertical sails, and the error grew with the rotation angle and the amount of stall. The global span lines are now used for global output. Results with body fixed output, without rotation, or without stall are unchanged. In a test with a wing at 60 degrees angle of attack and 72 degrees rotation around the x-axis, the total force was 19 % wrong before the fix.
- `SimulationResult::felt_velocity_minus_rotational_motion` added the felt velocity in the body fixed coordinate system to the rotational velocity in the global coordinate system when the output was in the body fixed coordinate system. The result is now always in the global coordinate system. This affected the apparent wind direction measured by the controller with `use_input_velocity` set to false and body fixed output, when the body was rotated.

- The angle of attack included the velocity component along the span, as it was the full angle between the chord and the velocity vector, rather than the angle in the plane normal to the span. A velocity along the span therefore increased the angle of attack. The velocity is now projected onto the plane normal to the span first. Simulations where the velocity had no component along the span are unchanged, which includes the iterative lifting line solver and the dynamic wake, which removed it already. Affected were:
  - The linearized solver, the default for quasi-steady lifting line simulations, when the freestream has a component along the span, e.g., for sails on a heeled or rolling ship. The velocity along the span was removed before the linear system was set up, but not from the velocity after the solution, which is used for the viscous correction of the circulation and for the forces. It is now removed there as well, in the same way as in the iterative solver. For a wing pitched 30 degrees relative to the freestream, the angle of attack was 30.2 degrees instead of 3.8 degrees.
  - The actuator line, when `remove_span_velocity` was false, which was the default.
  - The angle of attack measured by the controller in the `CompleteSailModel`, which is computed from the freestream velocity.
- With the output in the body fixed coordinate system, the residual of the lifting line solvers was computed with the body fixed span lines and the global velocity. The residual was wrong when the rigid body rotation tilted the span lines, e.g., roll or pitch, which changed when the iterative solver stopped. In a test with a pitch of 30 degrees, the residual was 5e-2 instead of 7e-5, and the forces changed by about 1e-4 relative. The residual is now always computed in the global coordinate system.
- `LineForceModel::projected_areas` and `total_projected_area` included the area of virtual line elements, which are not part of the wings. This affected the controller of active air flow sails, where the power for a set point of the section internal state was computed with the projected area, while the power is distributed over the area of the real line elements only. With virtual line elements, the controller therefore set a power that was too large, by the ratio between the total and the real area. `aspect_ratios` now also only includes the real line elements, both in the span and in the area.

### Changes
- The dynamic wake no longer looks up the wing index of each panel and point when the self-induced velocities are neglected. The split into self-induced and other-induced velocities is done in the `FrozenWake` with contiguous blocks of line elements, as the line elements of each wing are stored after each other, so the split has no measurable cost compared to computing the total velocity directly. There is now only one function for each type of induced velocity calculation, instead of separate functions for neglecting the self-induced velocities.
- New `lifting_line_correction_benchmark` test, ignored by default, that times the update and the evaluation of the lifting line correction with the `Straight`, `StraightPanels` and `Dynamic` wakes. With three wings with 40 line elements each, and 50 panels per line element, one call takes about 0.6 ms (isolated wings) and 1.8 ms (with wing interactions) with the `Straight` wake, and about 5 ms and 15 ms with the `StraightPanels` wake, or 2 ms and 4 ms with the `parallel` feature. The `Dynamic` wake with 100 panels costs about 1.5 times the `StraightPanels` wake with 50 panels.
- New `induced_velocity_benchmark` test, ignored by default, that times the induced velocity calculations in the frozen wake and full time steps of dynamic and quasi-steady simulations. Run it with `cargo test --release induced_velocity_benchmark -- --ignored --nocapture`, optionally with `--features parallel`.
- The documentation of the `DynamicWake` describes the order of the panels and points more precisely: the stream index is the outer index and the span index the inner index, so that the panels of each wing are one contiguous segment in each streamwise row.

## 0.13.1 - 2026-11-20
### Features
- New `internal_states` field in the `LineForceModelBuilder`, with one initial internal state for each wing, set as a constant value along the span. It is optional in JSON input, and the default, an empty list, gives the same initial internal state of zero as before. The values are kept until they are changed, e.g., by a controller. This makes it simpler to run simulations with a fixed internal state without a controller (no need to override the values manually in the CFD solver). Together with the existing `local_wing_angles`, the operating point of each wing can now be fully set in the builder.
- `LineForceModelBuilder::check_settings` checks that the number of `internal_states`, if given, matches the number of wings.

### Bug fixes
- The maximum change rate of the local wing angles in the controller (`max_local_wing_angle_change_rate`) did not account for the wrapping of the angles between -pi and pi. When the controller moved a wing angle across pi, e.g., from 179 to -179 degrees, the rate limit saw a change of -358 degrees instead of +2 degrees, and turned the wing by the maximum change in the wrong direction. This could lock the wings at an angle where the controller output stays at pi, far from the angle of attack set point, typically with stalled sails. It happens when the local wing angles that give the set point are close to pi, e.g., for sails with the chord vector pointing towards the bow in head winds. The change is now limited along the shortest way around the circle, with the new function `limit_angle`, and the limited angle is between -pi and pi. Nothing changes for angles away from pi, and the internal state still uses `limit_value`.
- `InternalFlow::internal_suction_from_flow_power` could return NaN for very small, but non-zero, powers, which then gave a panic with an index out of bounds in `VaryingFoil` (`the len is 5 but the index is 18446744073709551615`). This happened for suction sails with the `PowerToInternalFlow` conversion, e.g., with a controller loading close to, but not exactly, zero, such as 1e-16 from round-off. The root of the power balance is then so close to the threshold suction, where the flow starts, that the residual is constant or a staircase function in floating point, and the secant method divided by zero. The internal suction is now found with Brent's method, in a bracket from the threshold suction to an upper value that is increased until the power is exceeded, as already done for the fan based conversion. Tiny powers now give the threshold suction and zero suction coefficient, the same as zero power, and the results for normal powers are unchanged within the solver tolerance.
- `VaryingFoil` gives a clear panic message if the internal state is NaN, instead of an index out of bounds in the interpolation.

### Changes
- The OpenFOAM actuator line interface (`cpp_actuator_line` 0.13.1), pystormbird 0.13.1, Stormflow 0.4.1 and pystormflow 0.4.1 depend on this version. The new field is read through the JSON input, so the interfaces themselves are unchanged.

## 0.13.0 - 2026-11-14
### Breaking changes
- Invalid user input is now returned as errors rather than causing panics. The following functions return a `Result<_, Error>` instead of the value directly:
    - `LineForceModelBuilder::build` and `LineForceModelBuilder::build_with_nr_sections`
    - `WingBuilder::build`, `WingBuilder::internal_compartments`, `WingBuilder::gyroscopic_moment` and `WingBuilder::dynamic_stall`
    - `DynamicStallModelBuilder::build`
    - `DynamicWakeBuilder::build`
    - `SimulationBuilder::build`
    - `ActuatorLineBuilder::build`, `ActuatorLine::new_from_file` and `ActuatorLine::new_from_string`
    - `ActuatorLine::write_results`, which also returns errors from writing the CSV file with the forces, which were silently ignored before
    - `DiscretizedSpectrum::from_json_string` and `DiscretizedSpectrum::from_json_file`
    - `VelocityVariation::from_json_string` and `VelocityVariation::from_json_file`
    - `WindCondition::set_parallel_gust_from_json_string`, `WindCondition::set_perpendicular_gust_from_json_string` and `WindCondition::set_vertical_gust_from_json_string`
- Functions that returned errors as a `String` or a `serde_json::Error` now return the common `Error` type of the library, so that all errors can be propagated with `?`. This applies to `VaryingFoil::new`, `SpanVariation::new_linear`, `SpanVariation::new_piecewise_constant`, `InternalCompartments::new`, `FanCurveData::new`, `InternalFlow::new`, `SectionModel::from_string` and `ActiveAirFlowFoil::new_from_string`.
- New `InvalidInput` variant in the `Error` enum, see below. Code that matches exhaustively on the error must handle the new variant.
- Validation errors use the new `Error::InvalidInput` variant, rather than `Error::CustomStringError`. This includes the existing checks of the dynamic stall model, the dynamic wake, the spanwise measurements in the controller, and the use of dynamic stall in quasi-steady simulations.
- The `dynamic_stall` field in `SingleWing` holds the built `DynamicStallModel` rather than the `DynamicStallModelBuilder`, so that the model is built, and checked, in `WingBuilder::build`.
- `Simulation::new_from_string` and `CompleteSailModelBuilder::build` no longer call `SimulationBuilder::check_settings` separately, as the checks are done in `SimulationBuilder::build`.
- Depends on Stormath 0.5.0, where the `YawPitchRoll` rotation type is removed, as it was the same rotation as `XYZ`. Line force models with `"rotation_type": "YawPitchRoll"` in the JSON input give an error, and should use `XYZ` instead.
- `ControllerBuilder::build` returns an error if `time_steps_between_updates` is zero, which gave a division by zero when the controller was updated.
- The `GaussianSmoothing` variant of the `AngleOfAttackCorrection` is removed. It was not implemented, and gave a panic when it was used. The only variant is now `None`, which is the default. JSON input with `"GaussianSmoothing"` gives an error.
- New `allowed_relative_internal_state_error` field in the `CompleteSailModelSettings`, so code that creates the settings directly must set it, or use `..Default::default()`. The field has a default value when deserialized.
- The controller in the complete sail model is optional. The `controller` field in `CompleteSailModelBuilder` is an `Option<ControllerBuilder>`, and the `controller` field in `CompleteSailModel` is an `Option<Controller>`. JSON input with a controller works as before. Code that accesses the controller of the model directly must handle the `None` case.

### Features
- New `Error::InvalidInput` variant for invalid input or settings, with a helper constructor `Error::invalid_input`. The `Error` type also implements `std::error::Error::source` for the IO and JSON errors.
- New `WingBuilder::check_geometry` function, which checks that a wing has at least two section points, one chord vector for each section point, one `line_segment_is_virtual` value for each segment if given, at least one section, and a span larger than zero. Before, these cases gave index panics or invalid values when building the model.
- New `WingBuilder::check` function, which checks the geometry, the internal compartments, the gyroscopic moment model and the dynamic stall model of a wing.
- `LineForceModelBuilder::check_settings` checks that there is at least one wing, all the settings of each wing, and that the number of `local_wing_angles` matches the number of wings. New `LineForceModelBuilder::check_settings_with_nr_sections` for the same checks with a given number of sections. Errors from a wing include the index of the wing.
- `SimulationBuilder::check_settings` also checks the settings of the dynamic wake, if used.
- New `ActuatorLineBuilder::check_settings` function, which checks the settings of the line force model, and that `write_iterations_full_result` is not zero, which gave a division by zero when writing results before.
- New `Error::code` function, which returns a numeric code for each type of error (1: IO, 2: JSON, 3: invalid input, 4: custom string error), for interfaces that can only report errors as numbers, such as the FMU.
- The complete sail model can be used without a controller, which is mainly intended for time-domain simulations where the sail settings are given from the outside, such as in the FMU. Without a controller, the `apply_controller_*` functions do nothing, `simulate_steady_state_condition` runs a single simulation with the current local wing angles and internal states, and `simulate_optimal_steady_state_condition` runs a single simulation, as the loading has no effect.
- The `wind_environment` field in the `CompleteSailModelBuilder` is optional in JSON input, with the default wind environment as the default value, and the fields of the builder are public. The `thrust_direction` in the `CompleteSailModelSettings` is also optional in JSON input. Before, it was required whenever the settings were given.
- New functions on the `CompleteSailModel`:
    - `do_step_with_ship_velocity_vector` and `freestream_velocity_with_ship_velocity_vector`, which take the velocity of the ship as a vector, for cases where the ship does not move along the negative `zero_direction_vector` in the wind environment, e.g., when the ship velocity comes from an external motion simulation. The existing `do_step` and `freestream_velocity` use these functions, with the vector from the new `ship_velocity_vector` function, and give the same results as before.
    - `flow_measurements_from_simulation_result`, which returns the measured flow conditions on each sail, as input to a controller. It uses the spanwise measurement of the controller, if there is one, and a default spanwise measurement otherwise, so that the measurements are also available without a controller.
    - `update_controller`, which updates the controller with the given measurements and applies the output to the sails, `has_controller`, and `spanwise_measurement`.
- New `CompleteSailModel::simulate_steady_state_condition_with_ship_velocity_vector` and `CompleteSailModel::simulate_optimal_steady_state_condition_with_ship_velocity_vector`, with the ship velocity given as a vector. In the optimal version, the delivered power is the thrust times the component of the ship velocity along the `thrust_direction`. The versions with a scalar ship velocity give the same results as before.
- New `Controller::steady_state_output`, which gives the output directly from the set points, without input filters, rate limits, update interval or start time, and without changing the state of the controller. New `ControllerSetPoints::get_local_wing_angle_without_rate_limit` and `ControllerSetPoints::get_internal_state_without_rate_limit`.
- New `allowed_relative_internal_state_error` setting in the `CompleteSailModelSettings`, with a default value of 0.001, used in the convergence check of the steady state simulations.
- The `rotation_type` in the `LineForceModelBuilder` can be set to any of the rotation types in Stormath 0.5.0, i.e., the order of the rotations around the fixed axes: `XYZ` (default), `XZY`, `YXZ`, `YZX`, `ZXY` or `ZYX`.

### Bug fixes
- The angular velocity of the rigid body motion, computed with finite differences in `LineForceModel::set_translation_and_rotation_with_finite_difference_for_the_velocity`, was wrong when more than one rotation angle was different from zero, e.g., for a ship with a heading that rolls. The roll rate was then applied around the global x-axis rather than the x-axis of the ship. The fix is in Stormath 0.5.0, where the angular velocity is computed from the change in the rotation matrix. This affects the felt velocity on the sails, the gyroscopic moment, and the apparent wind direction measured by the controller. Results for rotations around a single axis are unchanged.
- The `rotation_type` in the `LineForceModelBuilder` was not used, so the model always used the default rotation type.
- The steady state simulations in the `CompleteSailModel` used the controller in the same way as in the time domain, with the iteration number as time and a time step of one. Input filters, rate limits, `time_steps_between_updates` and `start_time` in the controller therefore affected the result, and the state of the controller was kept between calls, so the result could depend on the earlier conditions that were simulated. The steady state simulations now use the new `Controller::steady_state_output`, and the result only depends on the input.
- The steady state simulations used the unsteady wind with the iteration number as time, so gusts in the wind condition made each iteration see a different wind. Only the steady part of the wind is now used.
- The steady state simulations only checked the local wing angles for convergence, and returned the result from before the last controller update. For sails where the controller only changes the internal state, such as rotor sails with the set point given as a spin ratio, the iterations stopped after the first simulation, and the result did not correspond to the final internal state. The convergence check now includes the internal states, and the result is from a simulation with the final settings.
- The inflow corrections in the `CompleteSailModel` were looked up with an apparent wind direction that only included the ship velocity, and not the linear motion of the sails. When the velocity of the ship was given as motion of the sails, e.g., through the translation in the FMU, the corrections were looked up at the true wind direction. The linear velocity of the rigid body motion is now included.

### Changes
- The linearized solver and `ActuatorLine::update_controller` use `expect` with a descriptive message, rather than `unwrap`, for the cases that can still panic: a singular equation system in the linearized solver, and updating the controller before the first time step in the actuator line model.

## 0.12.0 - 2026-10-31
### Breaking changes
- The default `wind_rotation_axis` in the `WindEnvironment` is changed from the positive to the negative z-axis, i.e., opposite of the default up direction, so that the wind direction is measured clockwise seen from above. This is the same default as in stormbird_setup, and the convention that is described in the book. Wind environments that are created from JSON without a `wind_rotation_axis` get the opposite sign of the wind direction. Set `wind_rotation_axis` to `{"x": 0.0, "y": 0.0, "z": 1.0}` to get the same behavior as before.
- The `EmpiricalCirculationCorrection` for actuator line simulations is renamed to `TipLossCorrection`, and the field in the `ActuatorLineBuilder` is renamed from `empirical_circulation_correction` to `tip_loss_correction`. The source file is renamed from `corrections/empirical_circulation.rs` to `corrections/tip_loss.rs`.
- The `overall_correction` factor in the correction is removed. The correction now rejects unknown fields, so input that still contains `overall_correction` gives an error.
- `LiftingLineCorrection::velocity_correction`, and the two functions `velocity_correction_isolated_wings` and `velocity_correction_all_wings`, take two circulation distributions instead of one: the circulation used for the forces on the wings, which is used in the reference model with the small viscous core, and the circulation used for the projected forces, which is used in the model with the viscous core equal to the projection width. Pass the same values for both to get the same behavior as before.
- `LineForceModel::lift_coefficients_pre_stall_with_stall_drop_off` and `LineForceModel::lift_coefficients_post_stall_with_stall_weight` are replaced by `LineForceModel::lift_coefficients_pre_and_post_stall`, which returns both parts as a tuple, so that the dynamic stall model is only evaluated once for each line element. The new function takes the velocity at the control points as a new, third, argument, as it is needed by the dynamic stall model.
- `SectionModel::lift_coefficient_pre_stall_with_stall_drop_off` and `SectionModel::lift_coefficient_post_stall_with_stall_weight` are replaced by `SectionModel::lift_coefficients_pre_and_post_stall`, which returns both parts as a tuple, and takes an optional amount of stall as a third argument. If no amount of stall is given, the static value from the foil model is used, as before. The functions with the same names on `Foil`, `VaryingFoil` and `ActiveAirFlowFoil` are kept.
- The unused `LineForceModel::lift_coefficients_total` function is removed, as it did not include the dynamic stall model.
- `SimulationBuilder::build` panics, and `Simulation::new_from_string` and `CompleteSailModelBuilder::build` return an error, if a wing has a dynamic stall model and the simulation settings are quasi-steady.
- New `amount_of_stall` field in the `SectionalForcesInput`, so code that creates the structure directly must set it. The field has a default value when deserialized, so results written by older versions can still be read.

### Features
- New, experimental, dynamic stall model for section models that build on the foil model, in the new `section_models::dynamic_stall` module. The model is based on the Leishman-Beddoes model, but adapted to the stall model in the foil model: the pressure lag is applied to the angle of attack, and the separation lag to the amount of stall, which replaces the Kirchhoff relationship. This makes the model valid for all angles of attack, and it always gives the static lift in steady conditions. It is set for each wing with the new, optional, `dynamic_stall` field in the `WingBuilder`, which takes a `DynamicStallModelBuilder` with the two time constants `pressure_time_constant` (default 1.7) and `separation_time_constant` (default 3.0). The model also includes the extra lift from a leading edge vortex, which is fed by the lift lost due to the dynamic stall, created when the lagged angle of attack exceeds the mean stall angle of the foil, and shed after a given non-dimensional time. This is controlled by two more parameters in the builder, `vortex_time_constant` (default 6.0) and `vortex_passage_time` (default 7.0), where a vortex time constant of zero turns the vortex off. The vortex lift is treated in the same way as the post-stall lift. The dynamic amount of stall is used for both the lift and the drag, while the vortex only affects the lift. The model is used in dynamic lifting line simulations and in actuator line simulations. See the dynamic stall chapter in the book for more.
- New `LineForceModel` functions for the dynamic stall model: `wing_dynamic_stall_states`, `has_dynamic_stall`, `set_dynamic_stall_time_step`, `reset_dynamic_stall` and `update_dynamic_stall_state`. The lifting line `Simulation` calls these in `do_step`, and the steady state functions of the `CompleteSailModel` reset the state before each iteration, so that the results are based on the static foil model.
- The dynamic stall model does not compute the forces itself. It gives the effects that enter the force coefficients, the lagged internal state, the dynamic amount of stall and the vortex lift, as a `DynamicStallInput`, through `DynamicStallSegmentState::input`. The line force model computes the lift and drag from the section model with the given internal state and amount of stall, and adds the vortex lift to the post-stall part. The inputs for all line elements are available from the new `LineForceModel::dynamic_stall_inputs`, and the internal states to use for the force coefficients from `LineForceModel::dynamic_internal_states`, which is also used for the linear lift in the linearized solver.
- Experimental time lag in the internal state of the section model in the dynamic stall model, set with the new `internal_state_time_constant` in the `DynamicStallModelBuilder` (default 0.0, i.e., off). The lagged internal state is used for the lift and drag, but not for the power. The lag is mostly intended for rotor sails, where the internal state is the spin ratio, and is the only part of the dynamic stall model that is used for section models that do not build on the foil model. The other parameters in the builder are now optional, and setting them for a section model that does not build on the foil model, such as a rotating cylinder, gives an error. `DynamicStallModel::is_supported` is replaced by `DynamicStallModel::uses_foil_stall_model`, and `DynamicStallModel::evaluate` takes the section model and the internal state instead of the foil model.
- `SectionModel::drag_coefficient` takes an optional amount of stall as a third argument, in the same way as `SectionModel::lift_coefficients_pre_and_post_stall`, and `LineForceModel::viscous_drag_coefficients` takes the velocity at the control points as a third argument, as it is needed by the dynamic stall model. New `Foil::drag_coefficient_with_amount_of_stall` function, which computes the drag for a given amount of stall.
- The dynamic stall model is used in actuator line simulations. `ActuatorLine::do_step` can be called several times per time step, e.g., in each outer iteration of the CFD solver, and uses the time to detect when a new time step starts. The state of the dynamic stall models is then updated from the force input of the last simulation result, before the new time step is set. No changes are needed in the CFD interfaces. `ActuatorLineBuilder::build` gives a warning if a wing has a dynamic stall model and the `damping_factor` in the `SolverSettings` is below one, as the damping acts as an additional time lag on the circulation.
- `LineForceModel::update_dynamic_stall_state` takes the `SectionalForcesInput` from the result of the time step, rather than the velocity at the control points, so that the state is based on the same angles of attack and internal states as the forces, even if the model is changed afterwards, e.g., by a controller.
- New `amount_of_stall` field in the `SectionalForcesInput`, with the amount of stall used for the lift and drag on each line element. This is the dynamic amount of stall for wings with a dynamic stall model, the static value from the foil model otherwise, and zero for section models that do not build on the foil model. It is computed by the new `LineForceModel::amounts_of_stall` function.
- New, public, `DynamicStallModel::deficiency_function`, which is the discrete deficiency function used for all the first order lags in the dynamic stall model, i.e., the pressure lag, the separation lag, and the vortex lift.
- New `Foil::lift_coefficients_pre_and_post_stall` function, which computes the pre-stall and post-stall lift coefficients for a given amount of stall. It is the single implementation of the blend between the two, used by both the static and the dynamic lift.
- New `SectionModel::foil` function, which returns the foil model for the given internal state, or `None` if the section model is not built on the foil model. The foil is borrowed for a `SingleElementFoil`, and interpolated for the varying foils.
- New `SimulationBuilder::check_settings` function, which checks that the simulation settings are consistent.
- Invalid dynamic stall models, i.e., negative time constants, or parameters for the stall in the foil model set for a section model that does not build on the foil model, give an error from `SimulationBuilder::check_settings`, and therefore also from `Simulation::new_from_string` and `CompleteSailModelBuilder::build`, rather than a panic when the model is built. The checks are done by the new `DynamicStallModelBuilder::check` and `DynamicStallModelBuilder::check_time_constants`, `WingBuilder::check_dynamic_stall` and `LineForceModelBuilder::check_settings` functions. Building the model directly with invalid settings still panics.
- New, experimental, `application` setting in the `TipLossCorrection`, which takes the new `TipLossApplication` enum. The default, `Circulation`, applies the correction to the estimated circulation, as before. With `ProjectedForces`, the correction is only applied to the circulation used for the forces that are projected to the CFD grid, while the forces on the wings are computed from the uncorrected circulation. The correction is then applied after the damping of the circulation. The lifting line correction uses the projected circulation in the model with the viscous core, and the uncorrected circulation in the reference model. The intended use is to stabilize actuator line simulations of rotor sails by smearing the tip vortices in the CFD domain, while keeping the lift-induced drag from the uncorrected circulation. The circulation used for the projected forces is stored in the new `projected_circulation_strength` field of the `ActuatorLine`.
- New `maintain_mean_value` setting in the `TipLossCorrection`, turned on by default. When it is on, the corrected circulation on each wing is scaled so that the mean value over the span, weighted with the length of each line segment, is the same as before the correction. The correction then redistributes the circulation from the ends of the wings towards the middle, rather than reducing it. If the mean value of the corrected circulation is close to zero, the scaling is skipped. Set `maintain_mean_value` to false to get the same behavior as before.
- New `LineForceModel::lift_coefficients_for_circulation` function, which returns the lift coefficient that the circulation strength should correspond to, i.e., the pre-stall lift, plus the post-stall lift if `include_viscous_lift_in_the_circulation` is used. It is used both when computing the circulation strength and the residual.

### Bug fixes
- The viscous correction in the linearized solver always scaled the circulation with the pre-stall lift only. With `include_viscous_lift_in_the_circulation`, there is no separate viscous lift force, so the post-stall lift, including the lift from the leading edge vortex in the dynamic stall model, was lost. The correction now uses `LineForceModel::lift_coefficients_for_circulation`, i.e., the same lift coefficient as the circulation strength in the iterative solver.
- The residual in the line force model, used for the convergence check in the solvers, always compared the lift coefficient from the circulation with the pre-stall lift only. With `include_viscous_lift_in_the_circulation`, the circulation also includes the post-stall lift, so the residual did not go to zero for a converged solution on stalled sections, and the solvers could then only stop on the circulation strength difference tolerance or the maximum number of iterations, and not on the residual tolerance. The reported residual was also misleading in these cases. The residual now uses the same lift coefficient as the circulation strength.

### Changes
- The logic for the tip loss correction is moved from the `ActuatorLine` structure to a new `apply` function on the `TipLossCorrection`.

## 0.11.1 - 2026-10-25
### Features
- Two new, experimental, settings in the `LiftingLineCorrectionBuilder` for actuator line simulations, both turned off by default:
    - `max_correction_ratio`: limits the magnitude of the velocity correction at each control point to a ratio of the magnitude of the sampled velocity. Without a limit, the correction can become larger than the freestream velocity at the ends of wings with a large circulation at the ends, such as rotor sails, which reduces the lift and can make the simulations unstable.
    - `virtual_extension_factors`: virtual extensions of each wing at the first and the last end, only included in the reference model with the small viscous core. The extensions carry the circulation of the outermost line element, and move the tip vortices away from the ends of the wing, which can be used to represent end plates.

### Changes
- The default `induced_velocity_correction_method` in the `Linearized` solver is now `NoCorrection` (was `FullCorrection`). With `FullCorrection`, the circulation is corrected for stall with the angles of attack from the linear solution, while the forces, including the post-stall lift, are calculated with the angles of attack from the corrected circulation. Right before stall, sections could then get both an almost unstalled circulation and post-stall lift, which showed up as a jump in the lift. With `NoCorrection`, the correction and the forces use the same angles of attack, and the lift is smooth through the stall. Models with stall that are tuned with the linearized solver may need to be retuned, or set `FullCorrection` explicitly to keep the old behavior. The initial solution in the `Iterative` solver, with `start_with_linearized_solution`, still uses `FullCorrection`, so that the results of the iterative solver are unchanged.

### Known issues
- The controller and the wind environment use different definitions of the apparent wind direction. The controller measures it for each wing around the span direction, while the wind environment, and the lookup of inflow corrections, measures it around the `wind_rotation_axis`. For sails built from the bottom to the top, with the default wind environment, the two have opposite signs. Set points that are mirrored between positive and negative apparent wind directions are not affected. A fix is targeted for the next release, which will require set points that are not mirrored to be updated.

## 0.11.0 - 2026-10-23
### Highlights
- New structure for the `ActiveAirFlowFoil` section model, intended for suction sails. It now consists of a `VaryingFoil` model for the lift and drag, together with an `InternalStateConversion` that defines how the wing internal state is converted to the internal state of the foil model. Four conversions are available:
    - `SuctionCoefficientDirect`: the wing internal state is the suction coefficient, used directly. Mostly useful for testing.
    - `PowerToPowerCoefficient`: the wing internal state is the power, converted to a power coefficient on each line element. This is the same behavior as for the `ActiveAirFlowFoil` in earlier versions.
    - `PowerToInternalFlow`: the wing internal state is the fan input power, converted to a suction coefficient on each line element using a new, simplified model of the internal flow in the sail, together with a constant fan efficiency. The internal flow model is based on a pressure balance over the porous surface, where the external pressure is a linear function of the suction coefficient, so that the suction coefficient on each line element is found directly, without iterations.
    - `FanSpeedToInternalFlow`: the wing internal state is the rotational speed of the fans, converted to a suction coefficient on each line element using the same internal flow model, together with a fan model based on fan curves. The fan curves can be given either as dimensional curves at a reference rotational speed and density, or as non-dimensional coefficients, and are scaled with the fan affinity laws. The fan model also supports multiple fans in parallel and pressure losses in the ducts between the sail and the fans.
- All section models can now compute a power coefficient. Foils return zero, the `ActiveAirFlowFoil` returns a value consistent with the power given as the wing internal state, and the `RotatingCylinder` uses a polynomial model, with default values from Tillig and Ringsberg (2020).
- Section models can also compute the power for a whole wing, through a new `wing_power` function. For most section models, this is the power coefficient integrated over the wing, while the `ActiveAirFlowFoil` with fan curves computes the power from the operating point of the fans.
- New default input power model, `FromSectionModelPowerCoefficient`, which computes the power for each wing from the section model.
- The controller can now take the internal state set points either in the units of the section model (e.g., spin ratio or suction coefficient), or directly as the wing internal state (e.g., power), through the new `internal_state_set_point_type` setting.
- The internal state of a wing can now vary along the span, through the new `WingInternalState` enum, which is either `Constant` or `SpanVarying`. The span variation is given as non-dimensional span locations and values, and is either linearly interpolated or piecewise constant. It does not need to match the resolution of the line elements. The old way of setting the internal state with one value per wing is kept, and is still what the controller uses. New functions are added for setting span varying internal states. For the power based conversions of the `ActiveAirFlowFoil`, a span varying internal state is interpreted as power per span length.
- Wings can be divided into sealed internal compartments along the span, through the new `internal_compartment_boundaries` field in the `WingBuilder`, for instance to model suction sails with several fans. Each compartment has its own internal pressure and fans, and is solved separately. Compartments are only allowed for section models with an internal flow model.
- Simplified tuning of the `Foil` model, which is also used by the `VaryingFoil` and `ActiveAirFlowFoil` models:
    - The minimum pre-stall drag is now always located at the zero-lift angle, found from the linear part of the lift. The second order drag term is computed from the linear lift divided by the initial lift slope, which is approximately the angle of attack relative to the zero-lift angle. This means that the location of the minimum drag automatically follows changes in camber, flap angle or suction, and no longer needs to be tuned separately.
    - The higher order term in the pre-stall lift was replaced by a reduction of the lift slope, to model separation that develops gradually before the full stall, for instance on a flap. The reduction is set with a factor between 0.0 (no reduction) and 1.0 (zero slope), an onset angle, and a transition range. The factor and onset angle can be set separately for positive and negative angles of attack. The transition is the integral of a sigmoid function, which gives a smooth lift curve, also at zero angle of attack.
- The foil model chapter in the book was extended with equations for the pre-stall lift, the pre-stall drag and the stall model, and the static example figure was replaced by an interactive plot where the parameters of the foil model can be adjusted with sliders.
- The `RotatingCylinder` section model is now a fully parametric model. The data based lift was replaced by a model with an initial lift slope, a different slope at high spin ratios, and a smooth transition between them, set by a transition spin ratio and a transition range. The transition is the integral of a sigmoid function, in the same way as the slope reduction in the `Foil` model, and the lift is an odd function of the spin ratio. The default parameters are fitted to the same CFD data as the old default lift data. The rotating cylinder chapter in the book was rewritten to describe the new model.
- The `VaryingFoil` model can now use one-sided data. If the internal state data only contains values with one sign, the foil is assumed to be symmetric with respect to the sign of the internal state, and an internal state with the opposite sign gives the mirrored foil at the absolute value of the internal state. This means that, for instance, data for a flap angle only has to be given for one side, and can consist of a single flap angle. Data with both positive and negative values is used directly, as before. The interpolation of the foil parameters is also faster, as the two neighboring foils are blended directly, rather than interpolating each parameter separately.
- The quasi-steady wake now keeps the horseshoe vortices and their strengths from the last time step, in a new `QuasiSteadyWake` structure. This means that the induced velocities at arbitrary points, and the export of the wake geometry as VTK data, are now available for both quasi-steady and dynamic wakes, through the `induced_velocities` and `wake_as_vtk` functions on the simulation. A quasi-steady wake is exported with one polygon per horseshoe vortex. The VTK export for both wake types uses a shared writer, and the output for the dynamic wake is unchanged.
- New wing level force models, which are set for each wing in the `WingBuilder`, independent of the section model, and are all turned off by default:
    - `force_correction`: a `ForceCorrection` structure for empirical corrections of the forces. For now, it contains the `lift_induced_drag_correction`, which adds a drag coefficient equal to the factor times the square of the lift coefficient. The lift coefficient is computed from the total lift force on each line element, i.e., the circulatory force and the viscous lift.
    - `added_mass`: an `AddedMass` strip theory model, with separate coefficients for the acceleration normal to and along the chord. The coefficients are relative to the added mass of a flat plate, so that the theoretical value is 1.0 for acceleration normal to a foil, and 1.0 in all directions for a circular cylinder.
    - `gyroscopic_moment`: a `GyroscopicMoment` model for rotor sails, set by the total moment of inertia of the rotor. Only allowed together with the `RotatingCylinder` section model.
- The force calculations chapter in the book has new sections on the force corrections, the added mass model and the gyroscopic moment model, including recommended values for the added mass coefficients, and a comparison between the lift-induced drag correction and virtual line segments.
- The controller can again apply a moving average to its input, through the `moving_average_window_size` setting in the `ControllerBuilder`. When the window size is larger than zero, the measured angle of attack, velocity and apparent wind direction for each wing are averaged over the given number of controller updates, so that the controller acts on a smoothed version of the flow conditions rather than the instantaneous values. The apparent wind direction is averaged through its sine and cosine, so that the average is correct also when the direction passes ±π. The filter is not used by default.

### Breaking changes
- The input format for the `ActiveAirFlowFoil` section model has changed. The `VaryingFoil` data must now be given in a `varying_foil` field, together with an `internal_state_conversion` field. To get the same behavior as before, use the `PowerToPowerCoefficient` conversion.
- The default input power model has changed from `NoPower` to `FromSectionModelPowerCoefficient`. This gives the same result for wing sails, but rotor sails without an explicit input power model will now get the power from the polynomial power model in the `RotatingCylinder`. Set the input power model to `NoPower` explicitly to get the old behavior.
- Fields in the controller set points were renamed to reflect that the set points are no longer always given in the units of the section model, and that the limits are applied to the wing internal state:
    - `section_model_internal_state_data` -> `internal_state_data`
    - `internal_state_max_value` -> `wing_internal_state_max_value`
    - `max_internal_state_change_rate` -> `wing_internal_state_max_change_rate`
- The `input_power` function on the line force model now takes the sectional force input as an argument, as the power can depend on the local flow conditions.
- Stormbird now depends on version 0.4.0 of Stormath, which adds a bracketed root-finding method (Brent's method), used to find the operating point of the fans. Stormath 0.4.0 requires Rust 1.85, which is therefore also the minimum supported Rust version for Stormbird, set through the new `rust-version` field.
- The `internal_state` field in the line force model is now a vector of `WingInternalState` rather than a vector of floats. Use `set_internal_state` to set constant values as before, and `internal_state_representative_values` to get one value per wing.
- Virtual line elements are no longer included in the power or in the flow through an `ActiveAirFlowFoil`. They still get the same type of internal state as the rest of the wing, so that the circulation stays consistent along the span. For the `PowerToPowerCoefficient` conversion, this means that the power is only distributed over the line elements that are not virtual.
- Changes to the fields of the `Foil` model. As unknown fields are not accepted, input that uses the removed fields must be updated:
    - `angle_cd_min` was removed, as the location of the minimum drag is now computed from the linear lift. This field also shifted the stall angles, which are now always measured from zero angle of attack. Use `mean_positive_stall_angle` and `mean_negative_stall_angle` to adjust the stall angles instead.
    - `cl_high_order_factor_positive`, `cl_high_order_factor_negative` and `cl_high_order_power` were removed, and replaced by `cl_slope_reduction_factor_positive`, `cl_slope_reduction_factor_negative`, `cl_slope_reduction_onset_angle_positive`, `cl_slope_reduction_onset_angle_negative` and `cl_slope_reduction_range`. The slope reduction is off by default.
    - For foils with camber, flap or suction, and a non-zero `cd_second_order_factor`, the pre-stall drag will be different from before, as the drag is now symmetric around the zero-lift angle.
    - `cd_bump_during_stall` and `cd_stall_angle_offset` were removed, as they were experimental and rarely used. The drag now always uses the same amount of stall as the lift, and there is no additional drag term during the stall transition.
- The `cdi_correction_factor` and `added_mass_factor` fields were removed from the `Foil` and `RotatingCylinder` section models, and the `moment_of_inertia_2d` field was removed from the `RotatingCylinder`, as they are properties of the whole wing rather than of the two-dimensional section. As unknown fields are not accepted, input that uses these fields must be updated:
    - `cdi_correction_factor` is replaced by `lift_induced_drag_correction` in the new `force_correction` field in the `WingBuilder`. The lift coefficient in the correction is now computed from the total lift force on each line element, rather than from the section model, which gives slightly different results, mainly after stall. The correction is also no longer included in the drag coefficient from the section models, e.g., when plotting the section model in Python.
    - `added_mass_factor` is replaced by the new `added_mass` field in the `WingBuilder`. The definition has changed: the old factor was multiplied with the density, the area of the line element and the acceleration, which means that it implicitly had the unit of length. The new coefficients are non-dimensional, and relative to the added mass of a flat plate. For foils, the old factor corresponds to a `normal_coefficient` of `4 * added_mass_factor / (pi * chord_length)`.
    - `moment_of_inertia_2d` is replaced by `moment_of_inertia` in the new `gyroscopic_moment` field in the `WingBuilder`, which is the total moment of inertia of the rotor, rather than the moment of inertia per span length.
- The gyroscopic effect is now computed as a pure moment. Previously, it was computed with the wrong units, stored as a sectional force, included in the total force, and used as a force when computing the moments. The `gyroscopic` field in the `SectionalForces` is renamed to `gyroscopic_moment`, is not included in the `total` force, and is added directly to the integrated moments. The `gyroscopic` field in the `IntegratedValues` is therefore always zero for the integrated forces.
- The `sectional_added_mass_force` function on the line force model no longer takes the internal states as an argument, and `sectional_gyroscopic_force` is replaced by `sectional_gyroscopic_moments`. The `added_mass_factor` function on the `SectionModel`, and the `added_mass_coefficient` functions on the section models, were removed.
- The `spin_ratio_data` and `cl_data` fields in the `RotatingCylinder` model were removed, and replaced by `cl_initial_slope`, `cl_high_spin_ratio_slope`, `cl_slope_transition_spin_ratio` and `cl_slope_transition_range`. As unknown fields are not accepted, input that uses the removed fields must be updated. The lift with the default parameters deviates up to about 0.4 in lift coefficient from the old default data.
- The default values of the `DynamicWakeBuilder` were synchronized with stormbird_setup. `last_panel_relative_length` is now 1.0 (was 0.25), as in stormbird_setup. Simulations set up directly with JSON, or through other interfaces than stormbird_setup, that relied on the old default must set this value explicitly. The `last_panel_value` in the `SinIncrease` viscous core length evolution now has a default value, `Relative(0.1)`, as in stormbird_setup.
- `VaryingFoil` models with only positive (or only negative) internal state data now give the mirrored foil for internal states with the opposite sign. Previously, the first (or last) foil in the data was used for these internal states. The input is also checked when it is read: the internal state data must be strictly increasing, contain at least one value, and have the same length as the foils data.
- The automatic export of the dynamic wake to files was removed, together with the `write_wake_data_to_file` and `wake_files_folder_path` settings in the `DynamicWakeBuilder`. As unknown fields are not accepted, input that uses these settings must be updated. The wake can instead be exported from the script that runs the simulation, with the `wake_as_vtk` function. `Simulation::dynamic_wake_as_vtk` is deprecated in favor of `Simulation::wake_as_vtk`, which returns the data directly rather than an `Option`, as all wakes can now be exported. `WakeData::QuasiSteady` now holds a `QuasiSteadyWake` rather than the `QuasiSteadyWakeSettings`.

- The `check_for_zero_linear_lift` function on the `Linearized` solver was removed. It was meant to skip the solver when there is no lift, but due to a bug it never did, so the results are unchanged.
- `EllipticalWing::lift_induced_angle_of_attach` was renamed to `EllipticalWing::lift_induced_angle_of_attack`, to fix a typo.

### Bug fixes
- The `moving_average_window_size` setting in the `ControllerBuilder` was accepted, but not used, since the restructuring of the controller in version 0.8.0.
- The initial shape of the dynamic wake, before the first time step, had a length proportional to the chord length squared, rather than the chord length, as the direction of the wake was not normalized. The wake is initialized again at the first time step, so this only affected the wake shape before the simulation started.
- The angular velocity computed from finite differences of the rotation was wrong when a rotation angle passed -π in the negative direction, i.e., jumped from close to -π to close to π. This is fixed in Stormath 0.4.0, and affects simulations where the rotation is set with `set_translation_and_rotation_with_finite_difference_for_the_velocity`.

## 0.6.0 - 2025-10-21
### Highlights
Internal rewrite of some functionality, with the goal of simplifying and speeding up the code. Some new features were also added.

- Now storing global versions of geometry data directly in the line force model. This was to, potentially, avoid unnecessary repeated transformations of the local geometry when evaluating the forces and updating the wake
- New linearized solver, as a faster alternative to the full non-linear solver.
- New ways (or rather, back to an old way) to create a steady wake; direct from horseshoe vortices, rather through a reduced dynamic wake structure as before. A little faster.
- Start of "complete sail model" functionality, where the goal is to collect the typical functionality needed to model a "complete" sail for route simulation. This includes a lifting line model for the sails, controllers and a model of the wind conditions.
- Added empirical models for input power to the line force model

## 0.5.2 - 2025-02-06
### Highlights
No significant changes to the core library. This update was mostly about small changes to the FMU version, to better facilitate hybrid testing of wind-powered ships. The background was the first test of Stormbird in a hybrid test campaign in the SeaZero project.

In particular, the interface to the FMU was changed to fit better with the needs in such experiments. This included the following:
- Possibility of applying Froude model scaling to the input (from model scale to full-scale) and output (from full-scale to model scale)
- All parameters were moved to separate JSON files. The reason was simply that the current lab software used for doing hybrid tests only supports float variables directly in the FMU. There was therefore a need to move all non-float parameters to a separate interface. To make the setup consistent, all parameters were therefore moved to a separate JSON file. The file path can still be specified in the FMU, but it also has a default value suitable for hybrid testing (the default value only makes sense for the hybrid testing setup, so please specify the path in any other case)
- Adding the possibility of specifying "translational velocity" as input to the FMU. This is an alternative to applying motion directly through updates to the position, and instead specify the motion velocity directly. That is, the velocity due to translational motion, not rotational (that might come later but was not necessary in this case)

## 0.5.1 - 2024-10-24
### Bug fixes
- Fixed a bug in the dynamic wake update. The last and first panels in the dynamic wake were not updated entirely correctly when the wing was moving. The last panel was only moved in the direction of the freestream velocity, if the last panel length was set to be longer than the time step would indicate, the motion became incorrect. The second panel behind the line force model was also updated wrong, as the position was integrated in time from the current version of the first panel, not the previous. This caused a small "bend" in the wake when the wing was moving.

## 0.5.0 - 2024-10-21
### Highlights
- Some internal clean up of methods and structures
- It is now possible to get forces in *either* a global coordinate system or a body-fixed coordinate system. The line force model has an additional field which specifies the coordinate system for the force output. This can be specified in the builder input JSON string. See the documentation for more.
- The FMU version was updated, in preparation for more active use in the future. Expect more updates to the FMU version in future releases.

### Bug fixes
- A bug was discovered related to how `local_wing_angles` were applied to the line force model. It previously rotated the wings in a global coordinate system, which caused errors when the position of the wings were different than zero.

## 0.4.0 - 2024-09-16
### Highlights
Mostly a restructuring of the internal data, with the goal of either simplifying, or preparing for new features in the future. However, some external changes were also necessary (see below).

- The dynamic and quasi-steady wake was merged into one common data structure. This makes it much easier to ensure that all functionality is synced between the two simulation modes
- The lifting line solver setup was rewritten, mostly to make it easier to incorporate new solvers in the future.
- A new interpolation mode was added to the actuator line simulations; it is now possible to use the built in interpolation in OpenFOAM, rather than Gaussian interpolation in Stormbird.
- Gaussian smoothing and prescribed circulation distribution was merged into one Enum - it does not make sense to use both of them at the same time, so now the user have to explicitly choose only one.
- The line force model must be created with hints on whether or not the circulation will be zero at the ends or not. This is useful for initialization and when applying circulation corrections.
- A new `prescribed_initialization` function was added so that the circulation strength can be initialized with a prescribed shape. This can sometimes reduce the number of iterations necessary.
- The Vec3 data structure was replaced with a more general structure called SpatialVector. The main reason is that this data structure is written to also be useful in other rust libraries, and it is practical with shared functionality
- Moved the velocity corrections from the wake model to the solver, to simplify the wake data structure.
